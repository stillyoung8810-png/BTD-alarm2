# Defensive Execution Protocol

이 스킬은 "수석 아키텍트(Gemini)"가 제공한 코드 리뷰 및 리팩토링 스니펫을 **그대로 복붙하지 않고**, 로컬 코드베이스와 타입 정보를 기준으로 방어적으로 검증·병합하는 절차를 정의한다.

적용 대상은 다음과 같다.
- 다른 에이전트(아키텍트)가 작성한 리뷰, 수정 제안, 리팩토링 스니펫
- 사용자가 붙여넣은 "아키텍트의 리뷰 및 지시사항" 블록

## 사용 시점

다음과 같은 문맥이 보이면 항상 이 스킬을 사용한다.

- "수석 아키텍트", "Architect", "Gemini"가 작성한 코드 리뷰/스니펫을 적용하라고 할 때
- 사용자 메시지에 "아키텍트의 리뷰 및 지시사항" 이라는 제목 또는 유사한 구문이 있을 때
- "로컬 환경 검증", "환각 필터링", "안전한 병합", "Safe Merge" 같이 방어적 적용을 요구하는 표현이 있을 때

이 스킬은 **"코드를 어떻게 바꿀지"를 정하는 것이 아니라**, 이미 제시된 제안/스니펫을 **로컬 기준으로 검증하고 필요한 부분만 안전하게 흡수**하는 역할을 한다.

---

## 전체 워크플로우 개요

아키텍트의 리뷰/스니펫이 주어졌을 때, 아래 3단계를 반드시 순서대로 수행한다.

1. **Local Fact-Check (환각 필터링)**
2. **Scope & Syntax Verification (스코프 및 문법 검증)**
3. **Safe Merge (안전한 병합)**

도중에 **로컬 코드와 상충하는 내용(환각)** 이 발견되면, 그대로 적용하지 말고 **사용자에게 먼저 간단히 리포트**한 뒤, 합리적인 대안을 제안한다.

---

## 1. Local Fact-Check (환각 필터링)

아키텍트가 "A 함수가 없다", "B 임포트가 누락되었다", "이 로직을 새로 만들어야 한다" 등 **로컬 사실에 대한 주장**을 했을 때, 무조건 아래 절차로 교차 검증한다.

1. **검색 범위 결정**
   - 지적이 특정 파일을 가리키면:
     - 해당 파일을 `Read`로 연 뒤, 필요한 경우 `Grep`으로 심볼 존재 여부를 확인한다.
   - 프로젝트 전반에 대한 지적이면:
     - `Grep` 또는 `SemanticSearch`로 워크스페이스 전체에서 심볼/타입/컴포넌트가 이미 존재하는지 확인한다.

2. **존재 여부 검증**
   - 함수, 변수, 타입, 컴포넌트, 훅, 유틸 함수, 상수, 임포트 등이 이미 로컬에 정의되어 있는지 확인한다.
   - "없다"고 단정한 대상이 실제로 **이미 존재하는 경우**:
     - 아키텍트의 해당 주장(또는 그 주장에 기반한 "새로 만들라"는 지시)은 **환각 가능성이 높다고 간주**한다.
     - 새로운 구현을 중복 생성하지 말고, **기존 구현을 재사용하거나 확장하는 방향**으로 설계한다.

3. **불일치 리포트 규칙**
   - 아키텍트의 지시가 로컬 코드와 상충하면, 다음과 같이 사용자에게 먼저 보고한다.
     - 어떤 심볼/로직이 이미 존재하는데도 "없다"고 주장했는지
     - 새로 만들라는 제안이 왜 중복/충돌을 일으키는지
   - 보고 형식 (요약):
     - **"아키텍트 지시 vs 로컬 현실"** 간의 차이점을 3~5줄 이내로 설명
     - 적용 시 예상되는 문제(중복 정의, 타입 충돌, 로직 중복 등)를 간단히 서술

4. **합의 없이는 파괴적 변경 금지**
   - 이런 환각이 발견된 상태에서, 기존 동작을 깨뜨릴 수 있는 변경(함수 삭제, 시그니처 변경, 상태 구조 변경 등)은 **사용자의 명시적 요청 없이 진행하지 않는다.**

---

## 2. Scope & Syntax Verification (스코프 검증)

아키텍트가 제공한 스니펫을 그대로 대상 파일에 붙여넣기 전에, **TypeScript/React 관점에서 스코프와 문법이 안전한지** 검증한다.

1. **스코프 체크**
   - 스니펫이 참조하는 모든 식별자(변수, 함수, 타입, 컴포넌트, 훅, 상수 등)에 대해 다음을 확인한다.
     - 현재 파일 내에서 정의되어 있는지
     - 다른 파일에서 임포트해야 하는지
     - 임포트가 필요하다면, 이미 존재하는 유틸/타입을 재사용할 수 있는지
   - 다음과 같은 경우는 **그대로 적용하지 말고 수정**한다.
     - 로컬에 없는 함수/타입을 당연히 있다고 가정하는 경우
     - 잘못된 경로로 임포트하는 경우
     - 현재 파일의 책임(SRP)을 벗어나는 거대한 비즈니스 로직이 스니펫에 섞여 있는 경우

2. **문법/타입 체크 (정신적 시뮬레이션)**
   - 실제 LSP 실행은 할 수 없지만, 다음 관점에서 에러를 미리 추론한다.
     - JSX 내에서 잘못된 태그 구조 또는 누락된 props
     - TypeScript 타입 불일치 (예: `onClick`에 `void`가 아닌 값을 반환하는 함수 전달 등)
     - 널/옵셔널 체이닝 누락으로 인한 잠재적 `undefined` 접근
   - 이 과정에서 기존 코드의 패턴(에러 처리, null 체크, 타입 가드 등)을 확인하고, 스니펫도 동일한 수준의 방어 로직을 갖추도록 보정한다.

3. **프로젝트 규칙과의 일치성**
   - 워크스페이스에 `.cursor/rules/` 또는 팀 규칙 문서가 있다면, 다음을 우선적으로 따른다.
     - 타입 사용 규칙 (`any` 금지, non-null assertion 금지 등)
     - i18n 규칙 (하드코딩 텍스트 금지 등)
     - React/상태 관리 규칙, 파일 구조 규칙 등
   - 아키텍트 스니펫이 이 규칙들과 충돌하면, **스니펫을 조정**하여 규칙을 우선시한다.

---

## 3. Safe Merge (안전한 병합)

검증을 통과한 스니펫만을 대상으로 **AST 수준 구조를 보존하는 방향**으로 병합한다. 절대 "전체 파일 교체"나 "큰 블록 통째로 덮어쓰기"를 하지 않는다.

1. **변경 단위 최소화**
   - 가능한 한 **함수/컴포넌트/블록 단위로만 수정**한다.
   - 이미 잘 동작하던 다른 로직(예: 접근성용 `onKeyDown`, 다른 전략 분기, 에러 핸들링 등)을 삭제/축소하지 않도록 한다.
   - 비슷한 패턴이 이미 존재하면:
     - 해당 패턴을 재사용하거나, 공통 유틸/컴포넌트로 추출하는 방향을 우선 고려한다.

2. **기존 로직 보호 규칙**
   - 아래와 같은 요소는 특별히 주의해서 유지한다.
     - A11y 관련 속성 및 핸들러 (`role`, `tabIndex`, `aria-*`, `onKeyDown` 등)
     - 다른 전략/기능의 분기문 및 설정(예: 다른 투자 전략, 다른 탭/뷰 제어 로직)
     - 공용 유틸리티 함수, 공용 타입, 공통 상수
   - 아키텍트 스니펫이 이들을 **덮어쓰는 형태**로 제안한다면:
     - 덮어쓰기 대신, 새로운 분기/옵션/props 추가 등 **확장 방식**으로 재설계한다.

3. **AST 수준 병합 마인드셋**
   - 실제 AST 도구를 사용하지 않더라도, 다음과 같은 사고 방식으로 코드를 수정한다.
     - "이 함수의 시그니처와 책임은 유지한 채, 내부 구현만 단계적으로 변경할 수 있는가?"
     - "이 컴포넌트의 props 계약을 깨지 않고 기능을 추가/변경할 수 있는가?"
     - "공통 훅/유틸로 로직을 추출해 중복 없이 재사용할 수 있는가?"

4. **부분 적용 허용**
   - 아키텍트 스니펫 전체를 그대로 적용할 필요는 없다.
   - 다음과 같이 **유용한 부분만 선별 적용**한다.
     - 유효한 타입 정의, 인터페이스, 유틸 함수
     - 개선된 에러 처리/검증 로직
     - UI/UX 개선 아이디어 중 기존 구조와 잘 맞는 부분
   - 나머지 부분은:
     - 로컬 상황과 맞지 않거나
     - 기존 구조를 과도하게 깨뜨리는 경우
     - => 적용하지 않고, 필요 시 사용자에게 그 이유를 간단히 설명한다.

## 리포트 규칙 (환각 또는 충돌 발견 시)

아키텍트의 지시 중 일부가 로컬 환경과 맞지 않거나, 기존 코드를 파괴할 위험이 있는 경우, 변경 전에 사용자에게 다음 형식으로 간단히 보고한다.

- **요약**: 1~2문장으로 어떤 부분이 문제인지 설명
- **상세**:
  - 아키텍트의 주장/지시 요약
  - 로컬 코드에서 실제로 확인한 내용
  - 둘 사이의 차이점
- **제안**:
  - 안전한 대안 (예: 기존 함수 확장, 옵션 추가, 조건부 분기 추가 등)

사용자가 별도로 다른 방향을 지시하지 않는 한, **더 안전한 쪽(기존 동작 보존, 타입 안전, 팀 규칙 준수)** 을 기본 선택지로 삼는다.

## 예시 시나리오

### 예시 1: "없는 함수"라고 지적했지만 실제로 존재하는 경우

1. 사용자 메시지:
   - "아키텍트가 `formatPrice` 함수가 없다고 해서 새로 만들라고 합니다."
2. 절차:
   - `Grep` 또는 `Read`로 워크스페이스를 검색해 `formatPrice`가 이미 있는지 확인한다.
   - 이미 `utils/number.ts` 등에 동일/유사 함수가 존재한다면:
     - 아키텍트의 "없다"는 지시는 환각으로 판단.
     - 새 함수를 만들지 않고, 기존 `formatPrice`를 재사용하도록 코드를 설계.
     - 필요하다면 기존 함수를 약간 확장(옵션 추가 등)하되, 시그니처 호환성을 유지.

### 예시 2: 기존 A11y 로직을 덮어쓰는 스니펫

1. 아키텍트 스니펫이 `div` 클릭 핸들러만 제안하고, `role`, `tabIndex`, `onKeyDown`, `aria-label` 등을 제거하려고 할 때:
   - 기존 코드에서 A11y 관련 속성을 확인한다.
   - 아키텍트 스니펫 적용 시 해당 속성이 사라진다면, 이 부분은 그대로 적용하지 않는다.
   - 대신:
     - 새 로직을 기존 A11y 설정 위에 **추가**하거나
     - 기존 핸들러 내부를 확장하는 방식으로 머지한다.

### 예시 3: 전략 분기 로직을 단순화하라는 지시

1. 아키텍트가 "VR 밴드 전략만 남기고 나머지 전략 분기를 지워라"와 같은 제안을 할 때:
   - 다른 전략이 실제로 사용 중인지, 다른 화면/컴포넌트와 연관되어 있는지 확인한다.
   - 공용 전략 스위치 로직을 삭제하면 다른 기능이 깨질 위험이 크므로:
     - 해당 제안은 기본적으로 거부하고, 사용자에게 파급효과를 설명한다.
     - 대신 VR 밴드 전략 관련 부분만 **추가/개선**하는 방향을 제안한다.

## 요약 체크리스트

아키텍트 스니펫을 적용하기 전에, 아래 항목을 항상 점검한다.

- [ ] 지적된 "없다/누락" 항목이 실제로 로컬에도 없는가? (Local Fact-Check)
- [ ] 동일/유사 기능이 이미 존재하는데 중복 구현을 만들고 있지는 않은가?
- [ ] 새 스니펫이 타입/스코프/넓이 관점에서 안전한가? (Scope & Syntax)
- [ ] 프로젝트의 팀 규칙(.cursor/rules 등)과 충돌하지 않는가?
- [ ] 기존 A11y, 다른 전략 분기, 공용 유틸/타입 등을 덮어쓰고 있지는 않은가? (Safe Merge)
- [ ] 환각/충돌이 있다면, 사용자에게 간단히 리포트할 준비가 되었는가?
